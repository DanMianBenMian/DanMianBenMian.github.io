RyConsole 更新日志

从 2026-07 的 v1 旧款，到 2026-09 全新的 V2 研究控制台（今天 95 个原生桥）的安全研究 harness —— 这里按版本记录每一次真实改动。最新版为 V2.4.32。

V2.4.322026-11-01最新
  • ★ Fig 握手 raw xpc 注入 —— CVE-2026-112706 跨沙盒读协议侧落地：Ry-JB 论坛帖 #19 方案 v2 实现。全程不依赖任何私有 / 特权 entitlement，只走正常签名 + 公开发行 API。
  • ① raw xpc 对象注入：xpcFromObj 支持 {"__raw":"0x…"} 直接把 xpc_object_t 塞进 xpc dict。护栏 = 桥侧托管白名单（g_xpcRawReg 存强引用保活，上限 256）：未登记的指针回 __raw-not-managed，杜绝野指针 retain 崩溃。
  • ② 协议构造下沉到桥：新增 xpcFigCreateMessage / xpcFigSetCFURL / xpcFigBeginEstablishing / xpcFigCreateRecipient / xpcRawRelease 五个原语，Fig* 符号由桥侧 dlopen+dlsym 解析（失败可重试），op 必须非 0（否则 *out=0 → SIGBUS，桥侧直接拒 op-must-be-nonzero）。
  • ③ xpcSendObj：把托管 raw 对象当整条消息发（JSON 表达不出带 endpoint 的 xpc dict，必须整对象走），回包同样抽 fd。
  • ④ xpcFigCreateRecipient 回传 msg2：原实现丢弃返回值 ⇒ 探针拿不到第二段消息 = 原语不可用，现改为返回 ptr（并登记托管表）。
  • ⑤ errDesc 服务端错误描述透传：reply 路径不再把错误压成无描述的 <error>，真机第一件事就能看到服务端真实拒因。
  • ★ 版本 2.4.32 / build 72，未签名 IPA 491,987 B，需全能签侧载。
  • ⚠ 待真机验证：按 xpcConn → xpcFigCreateMessage(op≠0) → xpcFigBeginEstablishing → xpcFigSetCFURL → xpcFigCreateRecipient → xpcSendObj 跑 Fig 握手，先看 errDesc；xpcFigCreateRecipient 的 4 参语义（返回寄存器 x0 vs out 槽 x1）两条路径桥侧都兼容，待实测收敛。

V2.4.302026-11-01
  • ★ WS1 iokit 桥缺陷 #2 修复：Ry-JB 论坛帖 #16 定位 callPtr 固定元数函数指针 ladder 上限 8 参，导致 IOConnectCallAsyncStructMethod（9 参）等所有 async 外部方法（如 IOSurfaceRoot sel 17）永久不可达——内核侧 async 入口才填 asyncReference，同步入口恒 NULL ⇒ 同步怎么调都 0xe00002c2。与 #1（outCnt 硬编码）同类：#1 是参数值写死，#2 是参数个数写死。

  • ⚠ 待真机 A/B 验收：① callPtr 9 参 IOConnectCallAsyncStructMethod sel 17 拿到真实 kr（0x0=注册成功、随后 sel 18 注销）；② sel 24/sel 30 OOL：structInDescriptor/structOutDescriptor 非 NULL（sel 30 权限门返 0xe00002c1 预期）；③ 回归：callPtr 8 参 IOConnectCallStructMethod sel 6 仍 kr=0/3176B。
V2.4.292026-11-01
  • ★ WS1 iokit 派发通道修复：Ry-JB 论坛帖 #15 定位 iokitCall / iokitCallStruct / iokitCallPort 三处把 IOConnectCallMethod 的 outCnt 硬编码 16，而内核派发器对 (scalarInputCount, structureInputSize, scalarOutputCount, structureOutputSize) 是逐个精确相等比对（非 ≥）。表里 scalarOut 绝大多数是 0/1/2/4，固定填 16 使第一道 scalarOutputCount 检查就挂，几乎 100% 返回 kIOReturnBadArgument(0xe00002c2)。这推翻了此前「WS3 真机 sel 0..15 全 0xe00002c2 是内核门禁 / selector 不存在」的判断——真因是桥侧硬编码。
  • ① 新增 iokitCallEx 原语：调用方按方法签名传期望 scalarOutCount（内核回写实际个数到 outCount），不再盲发 16；
  • ② callPtr 补 ret 别名：返回值统一补十进制 ret（旧版仅 value hex 串，JS 侧 krWhy(res.ret) 取不到数字、易误读成 KERN_SUCCESS）。

V2.4.282026-10-30
  • ★ WS1 代码审查：修 4 个真缺陷（纯质量层，不引入新攻击面、不碰内核）。V2.4.27 出包后真机从未跑过（设备桥不通），改为离线逐行审查，查出 4 个问题并在本版全部修掉。
  • ① 必崩 → 早退：iosurfaceRead / iosurfaceWrite 没检查 IOSurfaceGetBaseAddress 返回 NULL，直接空指针读 / memcpy（违反红线「只访问已映射区间」）。现补 if(!base) 早退：读路径返回 0 字节、写路径一个字节都不写。
  • ② 语义错 → 令牌表 gSurfLockTok：3 处 IOSurfaceUnlock 传的是 NULL seed，而 iOS 的 IOSurfaceUnlock(ref, options, seed*) 第三参必须回传 Lock 那次拿到的 seed —— 原来解锁语义错、锁计数泄漏。现用 handle→栈 的令牌表配对（Lock 压栈 / Unlock 出栈原样回传 / release 一并清理；用栈而非单值，是因为 IOSurface 的 Lock 可嵌套）。省略 seed 也能正确解锁，显式传则以显式值为准。
  • ③ 不可观测 → 接 ukr：IOSurfaceUnlock 的返回值 3 处全被丢弃，解锁失败静默、后续 Lock 莫名失败无从排查。现 read / write 路径接住 ukr 并返回自解释错误串。
  • ④ 桥表签名同步：iosurfaceUnlock 的 JS 桥签名没跟上原生改动 —— ObjC 少传参编译期不报错，会静默错位。现改 JSValue *seedV 收（同时规避 V2.4.19 的 undefined → NSNumber 坑）。
  • ★ 离线质量闸 22 项全绿（无 clang 环境下的替代编译检查：括号配平 / seed 语义 / unlock 返回值 / base 空检 / 令牌栈一致性 / 桥表签名 / 版本号）。二进制实证：①②③ 三处修复指纹在包内命中（_gSurfLockTok、IOSurfaceGetBaseAddress 返回 NULL（…）、IOSurfaceUnlock kr=%d（…）），同样四条在 2.4.27 包里全未命中，判别力成立。
  • ⚠ 取证铁律：Mach-O 里 @"..." 含非 ASCII ⇒ 落 __TEXT,__ustring（UTF-16LE），用「整包 NUL 分块抽 UTF-8 串」会系统性漏检 —— 曾据此误判「包是旧代码」，改 UTF-16LE 后结论反转。
